# Codex token benchmark — 2026-09-21

In this controlled location-search microbenchmark, `jgrep --ai -F` used
**24.9% fewer total Codex tokens** than `rg -F` while returning the same first
five locations for every task.

| Metric (three tasks, one repetition) | `rg` baseline | `jgrep --ai` | Reduction |
| --- | ---: | ---: | ---: |
| Total tokens (input + output) | 92,632 | 69,602 | **24.9%** |
| Non-cached input tokens | 33,892 | 8,947 | **73.6%** |
| Search-tool output characters | 99,281 | 2,703 | **97.3%** |

The total-token difference was 23,030 tokens. Both arms ran exactly one search
command per task over the same files, in deterministic path order. Codex's five
reported locations matched between the two arms for all three tasks.

## Environment

- Source: commit `e07fecd08953d7bb29b5258c12559318c91b9405`
- Codex CLI: `0.154.0`
- Model: `gpt-5.6-luna`, low reasoning effort
- jgrep: `0.1.1`
- Repetitions: 1
- Tasks: fixed-string searches for `localjev-grep`, `jgrep`, and `semantic`

The `rg` command was `rg --hidden --sort path -n -F -- NEEDLE .`. The jgrep
command was `jgrep --ai --ai-max-results 25 -r -F -e NEEDLE .`. `AGENTS.md`
was excluded from the temporary snapshot so it could not bias tool selection.
Every Codex session was ephemeral and read-only.

The full per-run commands, answers, and `turn.completed.usage` records are in
[`results/2026-09-21.json`](results/2026-09-21.json). The reproducible runner
and task definitions are in [`run.sh`](run.sh) and [`tasks.json`](tasks.json).

## Scope and limitations

This result shows the effect of omitting matched source text and bounding the
number of locations in three broad fixed-string searches on this repository.
It does not measure semantic-search quality, end-to-end coding quality, or
latency. It is one repetition with one Codex model, so model variance is not
estimated and the percentage should not be treated as a general guarantee.
